# 実測記録: 切り離し起動時の黙って終わる不具合の再現確認と `--json` イベント形式

## 目的

設計の前提としていた 2 つの未確認事項を、実機の Codex CLI で確認する。

1. 制御端末から標準入出力を切り離して `codex exec` を起動すると、終了コード 0・標準出力 0
   バイト・標準エラー 0 バイトで黙って終わる不具合（Issue #19945）が、手元の版で再現するか。
2. `codex exec --json` が実際に出力するイベントの形式（種別・フィールド構成）。

## 測定日・環境

- 測定日: 2026-08-01
- Codex CLI: `codex-cli 0.144.5`
- モデル: `gpt-5.6-sol`
- 思考の深さ（reasoning effort）: `medium`
- OS: macOS

## 測定手順

いずれの条件も、呼び出し元のシェルから独立させるため次の形で起動した。

1. 新しいセッションへ切り離す（`setsid` 相当。macOS には `setsid` コマンドが無いため、
   子プロセスの起動時にセッションを分離する属性を使う）。
2. 標準入力を `/dev/null` にする。
3. 標準出力・標準エラーをそれぞれファイルへリダイレクトする。
4. `codex exec` に短くない依頼文を渡し、1 回だけ実行して結果を記録する。

この操作を、以下の 3 条件でそれぞれ 1 回ずつ行った。

- **条件 A（切り離しのみ）**: 上記 1〜3 のみ。擬似端末は割り当てない。
- **条件 B（切り離し + 擬似端末）**: 条件 A に加えて `script -q /dev/null` 経由で擬似端末を
  割り当てる。
- **条件 C（切り離し + `--json`）**: 条件 A に `--json` オプションを加える（擬似端末は割り当てない）。

## 実測結果

| 条件 | 終了コード | 標準出力 | 標準エラー | 最終回答ファイル | 所要時間 |
|---|---|---|---|---|---|
| A: 切り離しのみ | 0 | 3 バイト | 677 バイト | 2 バイト | 12.3 秒 |
| B: 切り離し + 擬似端末 | 0 | 925 バイト | 0 バイト | 2 バイト | 8.9 秒 |
| C: 切り離し + `--json` | 0 | 2006 バイト（4 行） | 39 バイト | 1678 バイト | 17.7 秒 |

条件 B では、標準出力に ANSI 制御文字と `^D`（終端制御文字）が混入し、条件 A・C であれば
標準エラーに出る内容まで標準出力へ合流していた。擬似端末を割り当てない条件 A・C の方が
標準出力は素直な内容のままだった。

## 結論 1: 擬似端末の割り当てを引き続き必須とするか（ADR-003 の再確認）

**必須としない。既定では擬似端末を割り当てない。設定で有効化できる保険として残す
（ADR-003 改訂を参照）。**

理由は次の 2 点。

1. **Issue #19945 は 0.144.5 で再現しなかった。** 条件 A（擬似端末なし・単純な切り離しのみ）
   でも終了コード 0・出力ありで正常終了した。「切り離すと黙って死ぬ」という前提の不具合が、
   少なくとも手元の版では発生していない。
2. **擬似端末を割り当てると出力が悪化する。** 条件 B では標準出力に制御文字が混入し、
   本来標準エラーに出るはずの内容まで標準出力に合流した。割り当てないほうが出力は綺麗である。

不具合が将来の版で再発する可能性はゼロではないため、対策そのもの（擬似端末の割り当て）は
削除せず、設定項目で有効化できる保険として残す。既定は無効。

## 結論 2: `--json` の実イベント列

条件 C で観測できたイベントは、実行順に次の 4 行だった。

```json
{"type": "thread.started", "thread_id": "..."}
{"type": "turn.started"}
{"type": "item.completed", "item": {"id": "item_0", "type": "agent_message", "text": "..."}}
{"type": "turn.completed", "usage": {"input_tokens": 16530, "cached_input_tokens": 9984, "output_tokens": 350, "reasoning_output_tokens": 23}}
```

### 既知 6 種別との一致・不一致

`FD-exec-03.md` §16.3 が挙げる既知の 6 種別（`thread.started` / `turn.started` /
`item.started` / `item.completed` / `turn.completed` / `turn.failed`）と比較する。

- **観測できた 4 種別**: `thread.started` / `turn.started` / `item.completed` / `turn.completed`
- **本測定では観測されなかった 2 種別**: `item.started` / `turn.failed`
  - 道具（ファイル読み書き等のツール呼び出し）を使わない短い依頼だったための不在であり、
    これら 2 種別が存在しないと確認できたわけではない。

### フィールド構成

- 種別は JSON の `type` キーに入る。キー名自体が `event_type` になっているわけではない
  （`event_type` は仕様書側がこの値を指すときに使っている呼び名）。
- `item.completed` の `item` は `id` / `type` / `text` を持つ。
- `turn.completed` は `usage` を持ち、その中に `input_tokens` / `cached_input_tokens` /
  `output_tokens` / `reasoning_output_tokens` を持つ。

## 未解決事項

17.7 秒（条件 C）の実行でイベントは 4 件のみで、うち 3 件は開始直後にまとまって発生し、
残り 1 件は完了時だった。この依頼は道具を使わない短い実行だったため、道具を使わず考え続ける
長い実行では、その間イベントが 1 件も流れない区間が生じると見込まれる。

したがって、「一定時間イベントが流れないことをもって停滞とみなす」設計は、道具を使わない
長時間の分析を停滞と誤判定しうる。今回の設計では生死判定をファイルロックの取得可否で行うため
（ADR-004）、この誤判定の影響は受けない。ただし、イベントの間隔を使った別の判定（進捗表示など）
を将来追加する場合は、この特性を踏まえて閾値を運用開始後の実測で決める必要がある。
