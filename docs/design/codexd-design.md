# Codex 実行基盤 再設計書

## この文書について

この文書は、Codex CLI を長時間・非同期で実行するための常駐プロセスを設計する調査記録です。
2026-07-31 時点の調査結果を対象にしています。
本文の事実は、実ファイルまたは実コマンドで確認したものです。
未確認の事項と推測は、その旨を本文中で明記しています。
公開版では、利用環境を特定し得る名称、絶対パス、利用側の検査スクリプト名を一般化しています。

**作成日:** 2026-07-31
**対象:** 利用側の設定ディレクトリにある入口スクリプトと実行系サブコマンド群（計 13 ファイル・2,015 行）
**目的:** Codex CLI を Claude Code から呼ぶ仕組みを作り直し、10 回以上の改修で解決しなかった問題を構造から断つ
**開発:** 別プロジェクトで実施する
**推奨案:** B（常駐プロセスによる実行管理・Go 製）

## 0. この文書の読み方

- 第 1〜4 章が現状の事実。すべて実ファイル・実コマンドで確認したもので、推測は「推測」と明記している。
- 第 5 章が Codex CLI 側に既にある仕組み。**自作する範囲がここで大きく変わる。**

## 1. 何が起きているか

### 1.1 このツールの位置づけ

`codex.sh` は、Claude（Opus）が実装・レビュー・調査を Codex CLI（`codex exec`）へ委譲するときの
唯一の入口である。運用ルール上 `codex exec` の直接実行は禁止されており、すべての委譲がここを通る。

サブコマンドは 11 個（`review` / `impl` / `plan` / `research` / `read` / `status` / `logs` /
`cancel` / `doctor` / `cleanup` / `parallel`（廃止済み））。

### 1.2 2026-07-31 に起きた事故

Claude のサブエージェントが `codex.sh research` を 3 本起動した。サブエージェントは
Codex の完了を待たずに報告して終了した。

| 起きたこと | 詳細 |
|---|---|
| 3 本とも消えた | `exit-code` も `last-message.md` も `partial-output.md` も残らなかった |
| 残ったもの | `prompt.md` と 0 バイトの `stdout.log`、途中まで書かれた `stderr.log` だけ |
| 外から見た状態 | 「実行中」と区別がつかない |
| 実際の損失 | 約 50 分の待ち時間。同じ依頼の重複起動 3 本。誤った状態報告 2 回 |

**同日の午前に入れたばかりの回収の仕組み（タイムアウト時に `codex exec resume` で最終回答だけ取り戻す）は、
一度も実行されなかった。** シェルごと終了させられるため、そのコードに到達しないからである。

### 1.3 事故の直接原因

`research.sh` が実際の起動箇所。`review` / `plan` / `read` / `impl` も同じ形である。

```bash
set +e
PATH="${CODEX_GIT_STUB_DIR}:${PATH}" \
  "$timeout_cmd" "$timeout_resolved" \
  "$CODEX_BIN" exec --sandbox read-only $skip_flag ... \
    -C "$cwd" --output-last-message "$last_msg" \
    "$(cat "$prompt_path")" \
    < /dev/null > "$stdout_log" 2> "$stderr_log"
local rc=$?
set -e
```

- **呼び出し元シェルの中で同期実行している。** `nohup` / `setsid` / `disown` は 13 ファイルすべてに 0 件（実測）。
- **終了状態は関数の最後でしか書かない。** `research.sh` に到達しなければ `exit-code` は生まれない。
- **開始時点の情報を何も残していない。** PID・開始時刻・解決後の制限時間・モデル名のいずれも保存していない。
- **異常終了時に状態を残す仕組みがない。** シグナル受信時の後始末は全 5 サブコマンドに無い
  （`trap` は `impl.sh` の排他ロック解放が唯一で、これは別目的）。

## 3. 実測で確認した欠陥の一覧

Codex による全数監査（13 ファイル・2,015 行）で 20 件が挙がった。
危険度の高いものは作成者が実ファイルで確認し直している。

### 3.1 プロセスの生死・異常終了（最重要）

| ID | 欠陥 | 根拠 |
|---|---|---|
| P-01 | 起動元から切り離していない | 実行系 5 本すべて。`nohup` / `setsid` / `disown` が 0 件 |
| P-02 | タスクごとの PID を記録しない | PID を読むコードは旧方式用だけ（`status.sh` / `cancel.sh`） |
| P-03 | 異常終了時に状態を確定する処理がない | 唯一の `trap` は `impl.sh` のロック解放 |
| P-04 | タスク作成から状態確定まで、記録が何も無い区間が長い | 特に `impl` はロック取得・worktree 作成・依頼文構築を通過後にしか書かない |
| P-05 | 制御されたタイムアウト以外は回収処理に入らない | `research.sh` ほか。親シェルごと死ぬと実行されない |
| P-06 | 回収処理自体も同じ親シェルの中で動く | `common.sh`。回収中に親が死ぬと結果を書けない |
| P-07 | タイムアウト以外の中断では途中経過を保存しない | `common.sh` |
| P-08 | `impl` / `read` の終了コードが返却値と食い違う | `impl.sh` が生の値を先に書き、`:238` で変換する |
| P-09 | `impl` の成功 `0` が検証完了を意味しない | 終了コードを書いた後に範囲検査が走る |
| P-10 | `plan` の外部出力の失敗が状態に反映されない | `plan.sh` で `0` を書いた後にコピーする |
| P-11 | 状態ファイルの書き込みが中断に耐えない | 一時ファイル経由でなく直接書いている |
| P-12 | タスク ID が衝突しうる | `impl` / `plan` / `research` は「秒単位の時刻 + 題名」だけ |
| P-13 | タスクの置き場を排他的に作らない | `common.sh` は `mkdir -p` のみ |
| P-14 | 題名の文字を検査していない | `/` を含めると入れ子になり、一覧から見えなくなる |
| P-15 | 記録台帳が異常終了に耐えない | 台帳への追記は全検査の後（`impl.sh` / `review.sh`） |
| P-16 | 台帳の切り詰めに競合がある | `common.sh` |
| P-17 | 入口の設定でサブコマンド失敗時に後処理が飛ぶ | `codex.sh` のエラー時即時終了の設定により、後処理へ到達しない |
| P-18 | 自動削除が稼働中の worktree を壊しうる | `codex.sh` はロックも実行中の PID も見ずに削除する |
| P-19 | **自動削除が置き場そのものを消しうる** | `codex.sh` の検索に最小深さの指定がない（**作成者が実測で確認**）。置き場自身が 7 日を超えると全体が削除対象になる |
| P-20 | 明示的な削除も実行中かどうかを見ない | `cleanup.sh` |

**P-19 は現時点で実害が出ていない**（作業用置き場 が未作成であることを実測で確認）。
**ただし置き場が作られて 7 日経つと発生する。** 段階 0 で最優先に直す。

### 3.2 外部から状態を判別できない条件

| 状態 | 今どう判定しているか | 誤判定・判別不能になる条件 |
|---|---|---|
| 実行中 | 終了コードのファイルが無く、出力の更新が 20 分以内（`status.sh`） | **PID を見ていない。** 起動元と一緒に死んだ直後、試し実行、起動前エラーも 20 分間「実行中」に見える |
| 完了 | 終了コードが `0` | 成果物の有無・サイズを確認しない |
| 失敗 | 終了コードが `0`/`6`/`124` 以外 | `impl` / `read` のタイムアウト `137` を失敗として表示する |
| タイムアウト | 終了コードが `6` または `124` | `137` を認識しない。親シェル死亡ではファイル自体が無い |
| 起動元と一緒に死亡 | **判定手段が無い** | 約 20 分後にすべて同じ表示へ合流する |
| 中断 | 旧方式のみ対応 | **現行の単発タスクは中断できない**（PID を記録していないため） |

### 3.3 実装用サブコマンド固有の複雑さ

| 事実 | 常駐化したときの影響 |
|---|---|
| ロックの取得が排他的でない（`common.sh`） | 同時に走る 2 本が両方とも取得に成功しうる |
| ロックの持ち主が呼び出し元シェルの PID だけ | 常駐プロセスにすると、個別の作業が死んでもロックが生き続ける |
| 解放が「プロセス終了時」に結び付いている（`impl.sh`） | 同じプロセスを常駐させると、作業が終わっても解放されない |
| ロックのファイル名を保持する変数がプロセス内に 1 つだけ | 複数の作業を同時に扱うと、最後の 1 つしか解放できない |
| 経路の比較が文字列のまま（`common.sh`） | 同じ場所を指す別の書き方を重複と検知できない |

**常駐化では、ロックの持ち主を「作業単位」にし、解放を作業の終了に結び付ける必要がある。**

## 4. 現行の入口が守っている出力の約束（変更してはいけない）

タスクの置き場 `/tmp/codex-tasks/<task-id>/` の中身を、**12 本の検査スクリプトが直接読んでいる**（実測）。

| ファイル | 意味 |
|---|---|
| `prompt.md` | 依頼文。レビュー実績の判定に使われる |
| `last-message.md` | 最終回答。**中身があること = 成果あり**と判定される |
| `exit-code` | 終了コード。`124` / `6` はタイムアウト |
| `stdout.log` / `stderr.log` | 実行ログ |
| `partial-output.md` | タイムアウト時の途中経過 |
| `recovered-after-timeout` | 回収成功の印 |

利用側の検査スクリプトが 12 本あり、タスク出力を直接読んでいる。さらに記録台帳を読む検査スクリプトが 6 本ある。前者はレビュー実績、実行結果、ワークフロー上の品質条件を判定し、後者はレビュー実施の記録を品質の関門として利用する。

これらは「レビュー未実施のコミットを止める」「計画書の書き込みを止める」といった品質の関門である。

**これを変える案は、12 + 6 本すべての移行手順が設計に含まれていなければ採用しない。**

## 5. Codex CLI が既に持っている仕組み（自作の範囲が変わる）

**手元の `codex-cli 0.144.5` に対して実コマンドで確認した。** 以下は 0.144.5 時点の実測である
（この領域はバージョンによる差が大きい）。

### 5.1 途中経過を出す仕組みがある

`codex exec --json` が実在する（実測）。標準出力が 1 行 1 件の JSON になり、
`thread.started` / `turn.started` / `item.started` / `item.completed` / `turn.completed` / `turn.failed`
といったイベントが流れる。

**これは今回いちばん大きい発見である。**

- 現行は `--output-last-message`（完了時にしか書かれない）だけに頼っている。
  だから「最終ファイルが無い」＝「実行中か死亡か分からない」になる。
- `--json` を使えば、**イベントが流れていること自体が生存の証拠**になる。
  独自の生存信号を作る必要がない。
- 判定を「最終ファイルの有無」から「**イベントが止まったかどうか**」へ変えられる。

### 5.2 完了を外へ知らせる仕組みが 2 つある

| 仕組み | 内容 | 現状 |
|---|---|---|
| `notify` 設定 | ターン完了時に外部コマンドを JSON 付きで起動する | **既に別のアプリが占有している**（Codex の設定ファイル）。使うなら競合の解消が要る |
| ライフサイクルの `Stop` | セッション終了時にコマンドを起動する | **既に 5 種すべて設定済み**（実測） |

完了検知のために外から繰り返し問い合わせる必要がない。

### 5.3 セッションは自動では消えない

- 保存場所: Codex のセッション保存先YYYY/MM/DD/rollout-<日時>-<UUID>.jsonl`
- 手元に **1981 ファイル**、最古は 2026-05-07（約 3 か月前）が残存
- 保持期間を設定する仕組みは存在せず、要望は今も未対応

タイムアウト時の `codex exec resume` による回収は、**セッションが残っている限り後からでも実行できる。**
ただし `--ephemeral` を付けたセッションは resume できず、**エラーにならず黙って新しいセッションが始まる。**

### 5.4 常駐モードは実在する。ただし今すぐ乗るには早い

| サブコマンド | 状態 |
|---|---|
| `codex mcp-server` | 正式 |
| `codex app-server`（`--listen` で stdio / unix ソケット / ws を選べる） | 実験的 |
| `codex app-server daemon`（`bootstrap` / `start` / `stop` ほか） | 実験的 |
| `codex exec-server` | 実験的 |
| `codex remote-control` | 実験的 |

（すべて 0.144.5 の `codex --help` で実在を確認）

**`codex app-server daemon` は、今回作ろうとしているものとほぼ同じ問題を、Codex 自身が既に解いている。**
公式の説明によれば「プロセス記録ファイル + ファイルロック」でデーモン化し、
各コマンドが JSON を 1 個返す設計になっている。

**それでも今すぐ土台にはしない。** すべて実験的表記のままで、
プロトコルの説明が実装に追いついていないという未解決の問題が複数あり、
デスクトップアプリと制御が競合する不具合も報告されている。

**ただし「プロセス記録 + ファイルロックで生死を管理し、各コマンドが JSON を 1 個返す」という設計は、
公式が採った答えなので、自作する際はこれを手本にする。**

### 5.5 最大の危険: 切り離すと黙って死ぬ不具合がある

> **Issue #19945（未解決）: 制御端末から標準入出力を切り離すと、`codex exec` が
> 終了コード 0・標準出力 0 バイト・標準エラー 0 バイトで黙って終わる（0.124.0 以降）**

- **今回やろうとしている「切り離し」がまさにこれに当たる。**
- 有効な回避策: 擬似端末を割り当て直す（`script -qfc "codex exec ..." /dev/null`）
- **効かない回避策: パイプ経由（`tee` / `tail`）**
- 手元の 0.144.5 で直っているかは**未検証**（第 13 章の最優先項目）

`/usr/bin/script` は実在する（実測）。

### 5.6 出力をファイルへ向けると更新が止まって見える

標準出力はファイルやパイプへ向けた瞬間に、まとめ書き（数 KB 溜まるまで書かれない）になる。
**「ログの更新時刻が新しいから生きている」という判定は、出力の少ない処理では誤検知する。**

`/usr/bin/stdbuf` が macOS に標準搭載されていることを実測で確認した（FreeBSD 版）。
`stdbuf -oL` で 1 行ごとの書き出しに変えられる。

## 6. macOS 側の制約（実測で確認）

| 事実 | 影響 |
|---|---|
| **`setsid` コマンドは存在しない**（`setsid not found`・実測） | シェルだけで確実な切り離しはできない。言語側の呼び出しか起動管理の仕組みが要る |
| `nohup` は終了信号を無視させるだけで、セッションもプロセスグループも変えない | 切り離しの手段としては不十分 |
| `disown` はシェル内部の管理表から外すだけで、OS 側は何も変わらない | 同上 |
| **起動管理の仕組み（launchd）は、ジョブ終了時にプロセスグループ全体へ終了信号を送る**（Apple TN2083） | **対策せずに移すと、管理側が終わった瞬間に Codex も巻き添えになる。今回の道連れ問題がそのまま再発する** |
| 起動管理の仕組みが起動したプロセスは、自分でデーモン化してはいけない（同 TN2083） | 二重にデーモン化すると死んだと誤認される |
| macOS の PID は狭い範囲を巡回する（実測で稼働中の最大 PID が 99961） | PID 番号の比較だけでは生死を誤判定する |
| ファイルロックはプロセス終了時にカーネルが自動で解放する | **生死判定の最も確実な手段。取りに行けたら死んでいる、取れなければ生きている** |
| ログアウトすると利用者ごとの常駐プロセスは止まる | ログアウト後も動かすなら別の登録先が要る（今回は不要） |

## 7. 要件

優先度順。P0 を満たさない案は採用しない。

### P0

1. **Codex の生存を起動元から切り離す。** 起動元（サブエージェント・中断されたツール呼び出し）が
   死んでも実行が続くこと。
2. **切り離しても黙って死なないこと。** 第 5.5 章の不具合への対策（擬似端末の割り当て）を

3. **状態を開始時に書く。** PID・開始時刻・解決後の制限時間・モデル名を起動直後に保存し、
   異常終了時も終了状態を必ず残すこと。
4. **「実行中」と「死亡」を推定でなく事実として区別できること。**

6. **第 4 章の出力の約束を維持する。** 変える場合は 12 + 6 本の移行手順を含めること。

### P1

7. **途中経過を実行中も残す。** `--json` のイベント列を使い、完了時にしか書かれない
   最終ファイルへの依存をやめる。
8. **現行の単発タスクを中断できるようにする。** 今は中断手段が無い。
9. **サブコマンド間の引数・制限時間・終了コードの扱いを統一する。**

### P2

10. **文書とコードの食い違いを機械で検査する。**
11. **モデル・思考の深さを変えたときに、軽い疎通確認を自動で行う。**

### 推奨は B

**理由（3 行）:** 今回の事故の原因は「Codex の親が、いつ消えるか分からない呼び出し元シェルであること」で、
これは A では監視役自身が無保護の孤児になるため解決しきれない。
B' は実行管理の部分を省けるが、**Codex 固有の事情（`--json` の解釈・resume での回収・
切り離しの不具合の回避・出力の約束の維持）はどのみち自作が残り**、外部ツールへの追随が新しい負債になる。

### B' を採らない理由（詳しく）

pueue は「デーモン + ソケットで長時間コマンドを管理し、外から状態を問い合わせる」中核を
1 コマンドで導入できる、現時点で唯一の既製品である。ただし今回の対象は汎用コマンドではなく Codex であり、
次がすべて残る。

1. 出力の約束（第 4 章）は pueue の形式と違うため、変換層を自作する
2. `--json` のイベントを読んで状態に落とす部分は自作する
3. タイムアウト時に resume で回収する判断は自作する
4. 切り離しの不具合への対策（擬似端末）は自作する
5. **デーモンが落ちた瞬間に実行中の子がどうなるかが、公式の資料で確認できなかった**
6. 不正終了後にプロセス記録の残骸を誤判定して起動自体に失敗する不具合が報告されている

**残る自作が B の半分程度あり、そのうえ外部ツールの版に追随する手間が増える。**
規模の差（4〜6 日 vs 7〜10 日）ほどの利得がない。

### C を今やらない理由

利用者 1 人・同時 4 本の規模では、画面が解決する問題（一覧・進捗・中断）は
`status` と `cancel` の改善で足りる。B の通信の口を「後から画面を足せる形」にしておけば、
C は必要になった時点で追加できる。

### A を選ばない理由

A でも今日の事故は止まる。しかし A は「監視役自身が無保護な子シェル」であり、
監視役が死んだときに誰も気づかない構造が残る。第 2 章のとおり、
**設定変更と個別対処を 12 回繰り返して良くならず、構造に手を入れた 2 回だけが根絶に成功している。**
A は 11 回目の個別対処になる。

**ただし A の一部は B の前に入れる**（第 10 章）。

## 9. 推奨案 B の設計

### 9.1 全体の構成

```
Claude Code / サブエージェント
        |
        v
codex.sh（薄い入口・引数の検査と後方互換だけ担当）
        |  Unix ドメインソケット（利用者専用の実行時ディレクトリ内・権限は本人のみ）
        |  1 行 1 件の JSON（submit / status / cancel / tail / ping）
        v
codexd（Go 製・常駐・起動管理の仕組みで自動再起動）
  ├─ 待ち行列と状態管理（遷移のたびにディスクへ保存）
  ├─ 実行係: script で擬似端末を割り当てて codex exec --json を起動
  │          子は新しいセッションにして、管理側の終了信号が伝わらないようにする
  ├─ 監視係: イベント列を読み、最終イベントの時刻を記録。終了を即時検知
  ├─ 生存の記録: タスクごとのロックファイルを保持（終了で自動解放）
  ├─ 約束の書き込み係: /tmp/codex-tasks/<task-id>/ へ現行と同一形式で出力
  ├─ 回収係: タイムアウト時の resume による回収 / 途中経過の保存
  └─ ロック係: 実装用サブコマンドの経路重複の検査（持ち主は作業単位）
        |
        v
codex exec --json（Codex CLI）
```

- 入口 `codex.sh` は依頼をソケットへ送り、完了までソケットを読みながら待つ（**見た目は現行と同じ**）。
  入口が途中で殺されても常駐プロセス側の実行は続き、ファイルは必ず書かれる。
- ソケットが無い（常駐プロセスが停止している）場合、入口は従来のシェル実行へ自動で切り替える。
  **これが切り戻しの手段を兼ねる。**

### 9.2 起動のしかた（第 5.5 章・第 6 章への対策）

**この 3 つを同時に満たす必要がある。1 つ欠けると別の形で同じ事故が起きる。**

1. **擬似端末を割り当てる。** `script -q /dev/null codex exec --json ...` の形で起動する。
   切り離した標準入出力のままだと、Codex が黙って終了する不具合（Issue #19945・未解決）に当たる。
   パイプ経由の回避は効かない。
2. **子を新しいセッションにする。** Go の場合は子プロセスの属性に指定するだけで済む（1 行）。
   `setsid` コマンドは macOS に存在しないため、シェルでは書けない。
3. **管理側の終了信号が子へ伝わらないようにする。** 起動管理の仕組みはジョブ終了時に
   プロセスグループ全体へ終了信号を送る（Apple TN2083）。2 の対策がこれも兼ねる。

あわせて、書き出しがまとめ書きにならないよう `stdbuf -oL` を挟む（macOS に標準搭載・実測確認済み）。

### 9.3 起動直後に必ず記録するもの

`<task-id>/task.json` へ次を書く（現状「開始時点の情報を何も残していない」欠陥への対策）。

PID / プロセス開始時刻 / 解決後の制限時間 / モデル名 / 依頼の開始時刻 / 経路（新旧どちらで走ったか）。

### 9.4 生死の判定（最重要要件）

**判定はファイルロックで行う。PID 番号の比較はしない。**

- タスクごとにロックファイルを持ち、実行中は常駐プロセスが排他ロックを保持する。
- 外から見るときは、そのロックを取りに行く。
  **取れてしまえば死んでいる。取れなければ生きている。**
- カーネルがプロセス終了時に自動で解放するため、**PID の使い回しによる誤判定が原理的に起きない。**
  macOS の PID は狭い範囲を巡回しており（実測で稼働中の最大 PID が 99961）、番号の比較は危険である。
- Codex 自身の常駐モードも、pueue も、この系統の方式を採っている。

**生死と停滞を別の軸として扱う。**

| 軸 | 判定方法 |
|---|---|
| 生きているか | ロックが取れないこと |
| 進んでいるか | `--json` の最終イベントからの経過時間 |

現行はこの 2 つを「ログの更新時刻が 20 分以内か」という 1 つの推定で混ぜている。
しかも出力をファイルへ向けるとまとめ書きになるため、その推定自体が誤りやすい（第 5.6 章）。

### 9.5 状態の定義

```
queued → starting → running ─┬→ completed        （終了・最終回答あり）
                             ├→ failed           （終了・最終回答なし、または終了コードが 0 以外）
                             ├→ timeout → recovering ─┬→ recovered
                             │                        └→ timeout-lost
                             ├→ cancelling → killed
                             └→（常駐プロセス再起動）adopted → 上のいずれか
running / adopted でロックが取れる（＝死亡）かつ終了コード未取得 → orphaned → recovering → recovered / lost
```

| 状態 | 判定の根拠 |
|---|---|
| queued | 待ち行列（同時実行 4 本の上限待ち） |
| starting | 起動直後 |
| running | **ロックが取れない**（生存）+ 終了イベント未着 |
| stalled | 生存しているが `--json` のイベントが 20 分以上止まっている。**殺さず警告表示のみ** |
| completed | 終了 + **最終回答の中身がある**（終了コードだけを根拠にしない） |
| failed | 終了 + 最終回答が空、または終了コードが 0 以外 |
| timeout | 常駐プロセス自身が停止させたので確実 |
| recovering / recovered / timeout-lost | resume による回収の中 / 成功 / 失敗 |
| cancelling / killed | 中断要求の受理 / 完了 |
| orphaned | 終了を看取れなかった（再起動時の確認で判明） |

**`completed` の判定に最終回答の中身を含めるのが要件 P0-5 への対策である。**
Codex には「実作業をせずに終了コード 0 で終わる」不具合が報告されており、
終了コードだけを成否の根拠にできない。

### 9.6 常駐プロセスが落ちたとき

- **子の Codex は殺さない。** 9.2 の 2 により、管理側の終了信号は子へ伝わらない。
- **再起動後の引き取り**: 起動時に全タスクの `task.json` を読み、実行中だったものについて
  ロックを取りに行く。
  - 取れない（生きている）→ 終了の監視を再開する。ただし自分の子ではないため終了コードは取れない。
    終了を検知したら、最終回答の中身があれば `0`、無ければ resume で回収を試み、
    それも失敗なら `1` を書く。**推定であることを示す印（`adopted-after-restart`）を必ず残す。**
  - 取れる（死んでいる）→ resume で回収を試み、失敗なら途中経過を保存して `1` を書く。
- **「終了コードが永久に書かれない」状態を仕組みの上で無くす。**

セッションは自動で消えないため（第 5.3 章）、**回収は後からでも実行できる。**
ただし `--ephemeral` を付けると resume できないので、**全サブコマンドで付けない**
（現在 `impl` と `read` だけが付けている。第 2.6 章）。

### 9.7 出力の約束の維持

- **常駐プロセスが直接書く。** 入口には書かせない（入口が死んでも約束が守られることが目的のため）。
- 記録台帳への追記は、現在それを行っている側の位置づけを変えない。
  常駐プロセスの責任範囲を「プロセスとタスクの置き場」に限定することで、
  **検査スクリプト 18 本は 1 行も変えずに済む。**
- 追加するファイルは**追加のみ**（`task.json` / `events.jsonl` / `adopted-after-restart` など）。
- **将来変える場合の手順**: (1) 新旧両方の形式を並行して書く期間を設ける →
  (2) 検査スクリプトを 1 本ずつ移し、移行済みの一覧を管理する →
  (3) 18 本すべての移行を確認してから旧形式の出力を止める。

### 9.8 言語: Go

| 観点 | 理由 |
|---|---|
| 切り離し | 子プロセスの属性に**新しいセッションにする指定を 1 行**書くだけ。Rust は安全でない書き方が必須、Swift は低レベルの記述が必要 |
| ソケットと JSON | どちらも標準機能だけで済む |
| 配布 | 追加の依存を引き込みにくい。**Apple は完全な静的リンクを認めていない**ため 3 言語とも共通の制約はあるが、Go が最も安全 |
| 署名 | 自分の Mac でビルドして自分で動かすだけなら手続きは不要。ビルド時に最小限の署名が自動で付く |
| 保守 | 読みやすく、テストも標準の仕組みだけで完結する |

**第 6 章の「起動管理の仕組みが子まで殺す」への対策を、Go は 1 行で書ける。**
これが 3 言語で最も差の出る点である。将来 C（画面）を作る場合も、
画面だけ別言語で書いて同じソケットに繋げばよく、Go を選んでも道は塞がらない。

### 9.9 通信: Unix ドメインソケット + 1 行 1 件の JSON

- 選ぶ理由: (a) 依頼と応答の往復ができる、(b) ファイル権限で本人限定にできる、
  (c) 複数の接続を自然に扱える、(d) 将来の画面も同じ口で繋げる。
- 動詞は 5 つに絞る: `submit` / `status` / `cancel` / `tail` / `ping`。
- **各コマンドは成功時に JSON を 1 個だけ返す**（Codex 自身の常駐モードと同じ流儀）。
- `submit` の応答でタスク ID を返し、以後は完了まで同じ接続を読み続ける。
  **接続が切れても実行には影響しない。**

### 9.10 サブコマンドの振り分け

| サブコマンド | 扱い | 理由 |
|---|---|---|
| impl / review / plan / research / read | 常駐プロセス経由 | 実行系。親の移転が目的そのもの |
| cancel | 常駐プロセス経由 | **現行の「中断できない」欠陥も同時に直る** |
| status | 入口で完結（ファイル読み）+ 常駐プロセスが応答すれば生死情報で上書き | 常駐プロセスが落ちていても最低限の一覧を出せることを優先 |
| logs / doctor / cleanup | 入口で完結 | `doctor` に「常駐プロセスの生存・ソケット応答・起動設定」の検査を追加 |
| parallel | 廃止のまま | 待ち行列が同時実行の制限を担う |

- **実装用の排他ロック**: 常駐プロセスが持つ。**持ち主は常駐プロセスではなく作業単位**にする
  （第 3.3 章の指摘への対策）。ロックファイル方式にすることで、
  現行の「死んだ PID のロック回収」の問題も消える。
- **worktree の作成・削除**: 常駐プロセスが持つ。同じ寿命の管理下に置けるため、
  P-18 / P-19 / P-20 の「稼働中でも消しうる」問題が解消する。

## 12. B の弱点と、それを受け入れる理由

1. **障害の影響範囲が広がる。** 常駐プロセスに不具合があると全タスクが巻き込まれる。
   - 受け入れる理由: 自動再起動と「常駐プロセスが死んでも Codex は死なない」設計で、
     最悪でも「新規受付が一時止まる」に被害を限定できる。入口の自動切り替えにより、
     停止中も従来経路で作業を続けられる。

2. **シェルより調査しにくくなる。** 今はファイルで全部追えるが、バイナリの内部は出したログしか見えない。
   - 受け入れる理由: 全状態遷移を `task.json` と `events.jsonl` へ書き出し、
     「ログに出ていないことは起きていない」と言える形にする。
     シェル 13 ファイル・落とし穴 45 件の現状より追跡しやすくなる見込み。

3. **入口と常駐プロセスの版がずれると壊れる。**
   - 受け入れる理由: 利用者 1 人・配布先 1 台なので同時更新で防げる。
     念のため応答に版番号を含め、不一致なら入口が旧経路へ落ちる。

4. **7〜10 日は、シェル修正 1〜2 日に比べて重い。**
   - 受け入れる理由: 2026-05-24 以降の 2 か月余りで 10 回以上の改修を行い、
     それでも今日の全損事故（3 本消失・誤報告 2 回・50 分の待ち）が起きた。
     改修と事故対応に既に費やした時間は 7〜10 日を超えている可能性が高い。
     段階 0 を先に入れるため、構築期間中も無防備にはならない。

5. **再起動後に引き取ったタスクは終了コードが推定になる。**
   - 受け入れる理由: 「常駐プロセスが落ち、かつその間にタスクが終わった」という
     二重の異常時に限られる。**現状は正常時ですら終了コードが消える。**
     推定であることを印で明示すれば、検査スクリプトが確定情報として誤用する事故も防げる。

6. **Codex CLI の版が上がると、`--json` のイベント形式や常駐モードの仕様が変わりうる。**
   - 受け入れる理由: イベントの読み取りは「知らない種類は無視する」設計にし、
     形式が増えても壊れないようにする。常駐モードには依存しない（自作する）。
